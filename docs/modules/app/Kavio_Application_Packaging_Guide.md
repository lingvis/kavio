# Kavio App Packaging Guide

> Public project entry: repository-root `./kavio`  
> Internal package writer: `kavio_app/tools/build_package.py`

## 1. Source project versus install package

Developers maintain one project descriptor:

```text
kavio_project.json
```

It combines build and package metadata but keeps those concerns logically separated:

```text
projectVersion
language
sdk
build
package
```

The public source project uses `kavio_project.json` as its project metadata source.

The package writer receives a prepared staging directory generated by the root project tool. Internal staging details are not part of the public project contract.

## 2. Source project layout

```text
MyApp/
├── kavio_project.json
├── icon.png
├── schema_description.json
└── device/
```

Only directories containing `kavio_project.json` are projects.

## 3. Package metadata source

The complete install/runtime metadata is under:

```json
"package": {
  "appId": "com.example.my-app",
  "version": "1.0.0",
  "name": "My App",
  "description": "...",
  "device": {
    "runtime": "native",
    "entry": "kavio_my_app",
    "arguments": []
  }
}
```

`package.device.runtime` is intentionally explicit even when the development language suggests a likely runtime. Language and process-launch runtime are different concepts.

Optional Host metadata:

```json
"host": {
  "binary": "host.dll",
  "panel": true
}
```

## 4. Build-only data is not packaged

Examples:

```text
language
build.source
build.target
```

These fields control development/build orchestration and are not copied into the install Manifest.

## 5. Final `.kap` layout

Typical package:

```text
manifest.json
icon.png
schema_description.json
device/
  <entry>
  lib/
  kavio/
host/
  host.dll
signature.json        # when signing is enabled
```

The package does not contain `kavio_project.json`.

## 6. `manifest.json`

Generated from `kavio_project.json.package` plus package-time facts.

The tool adds:

- current Manifest version;
- file list;
- byte sizes;
- SHA-256 for every distributed file;
- configuration metadata required by the Manifest format.

Developers do not edit `manifest.json` directly.

## 7. Icon

Fixed source path:

```text
<project>/icon.png
```

Requirements:

- PNG;
- width and height: 1～512;
- maximum 512 KiB;
- no symlink.

## 8. App Configuration definition

Fixed source path:

```text
<project>/schema_description.json
```

No configuration:

```json
{}
```

See `Kavio_App_Configuration_Spec.md` for the definition format.

## 9. Device runtime

### C++

```json
"device": {
  "runtime": "native",
  "entry": "kavio_my_app",
  "arguments": []
}
```

### Python

```json
"device": {
  "runtime": "python",
  "entry": "main.py",
  "arguments": [],
  "python": {
    "pythonVersion": "3.8",
    "installMode": "online",
    "requirements": "requirements.txt"
  }
}
```

### Lua

```json
"device": {
  "runtime": "native",
  "entry": "kavio_lua_runner",
  "arguments": ["main.lua"]
}
```

Lua uses the SDK native Runner as the process entry. The first argument identifies the Lua script.

## 10. Runtime dependencies

Projects do not list internal `.so` names.

The root tool derives the mandatory runtime from `language`, and UI runtime dependencies from native ELF linkage or Python/Lua source imports.

For example Python + UI automatically stages:

```text
libkavio_app_runtime.so
Python Core Binding
libkavio_ui_core.so
libkavio_ui_lvgl.so
Python UI Binding
```

## 11. Host Component

If `package.host` exists, the Host DLL is read from `build/apps/<project path>/host/`.
The project path is the directory containing
`kavio_project.json` relative to `kavio_app/`; it can be nested to any depth.

Example:

```json
"package": {
  "host": {
    "binary": "host.dll",
    "panel": true
  }
}
```

Run `./kavio build <project>` to create the project output folders. Copy the Windows-generated
`host/` directory into the matching `build/apps/<project path>/` folder. Any additional DLLs,
assets or subdirectories under `host/` are retained in the package. Device-specific additional
libraries and resources can be placed under `build/apps/<project path>/device/`, retaining their
relative paths under the package's `device/` directory. Files conflicting with SDK-provided
libraries or the entry executable cause packaging to fail rather than overwrite files.

`./kavio build` does not require the Host DLL; `./kavio pack` does.
The default package output is `build/apps/<project path>/dist/`.

## 12. Build/package flow

```text
kavio_project.json
        ↓
./kavio build <project>
        ↓
Device artifact/staged source
        ↓
./kavio pack <project>
        ↓
project package metadata + runtime dependencies + optional Host
        ↓
manifest generation + validation + SHA-256
        ↓
.kap
```

## 13. Commands

```bash
./kavio list
./kavio build MyApp
./kavio pack MyApp
```

Release:

```bash
./kavio build MyApp --release
./kavio pack MyApp --release
```

Override output:

```bash
./kavio pack MyApp --output /tmp/MyApp.kap
```

## 14. Validation principles

Packaging rejects:

- missing Device entry;
- missing required Python/Lua runtime files;
- missing declared Host artifact;
- invalid icon;
- invalid `schema_description.json`;
- unsafe relative paths;
- symlinks in packaged content;
- generated Manifest/signature files pre-existing in staging;
- files whose Manifest hash/size cannot be generated correctly.

## 15. What developers should edit

Edit:

```text
kavio_project.json
icon.png
schema_description.json
device source
```

Do not edit generated:

```text
manifest.json
build/
build/apps/<project path>/dist/*.kap
```
